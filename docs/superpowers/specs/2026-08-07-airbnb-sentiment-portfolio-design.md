## 1. Origin & attribution (non-negotiable)

This project is **not** framed as solo original research. It follows the pipeline
architecture and starter code from
[tkarim45/Beginner-Data-Science-Projects](https://github.com/tkarim45/Beginner-Data-Science-Projects)

- The source repo (owned by GitHub user `tkarim45`) contains the complete 4-stage
  pipeline (`1_dataPreprocessing.ipynb`, `2_machineLearning.ipynb`,
  `3_deepLearning.ipynb`, `4_LLM.ipynb`) plus `dashboard.py`/`charts.py`.
- The locally-held `2_machineLearning.ipynb` (which the repo owner has run before)
  contains NLTK download output referencing
  `/Users/taimourabdulkarim/miniforge3/envs/mlp/...` — the identical username and
  conda environment path that appears in the freshly-pulled `4_LLM.ipynb`.
- Stages 3 and 4 were, prior to this project, files the repo owner had never seen
  ("unknown contents").

**README requirement:** a "Credits / Origin" section near the top of the README
must state plainly that this project completes, debugges, and documents a public
tutorial pipeline by Taimour Karim, and link to the source repo. The portfolio
narrative is "took a broken/incomplete public tutorial pipeline to a genuinely
working, documented, tested state, sourced my own training data independently,
and analyzed why the results came out the way they did" — not "built from
scratch."

## 2. Data: source raw data independently

The true raw dataset referenced by the upstream `1_dataPreprocessing.ipynb`
(`Dataset/Uncleaned Data/clean_reviews.csv`, ~1.58M rows) does **not** exist in
the upstream repo (confirmed 404 via raw.githubusercontent.com). Its schema
(`listing_id, id, date, reviewer_id, reviewer_name, comments`), scale, and
content (London neighborhoods, multilingual reviews) match InsideAirbnb's public
London "detailed reviews" dataset.

Plan:
- Download InsideAirbnb's London detailed-reviews snapshot, e.g.
  `https://data.insideairbnb.com/united-kingdom/england/london/2026-06-19/data/reviews.csv.gz`
  (~277MB compressed, confirmed via HEAD request; latest snapshot as of this
  writing). InsideAirbnb publishes a new dated snapshot periodically, so the
  download step should read the date from InsideAirbnb's data listing rather
  than hardcode `2026-06-19` indefinitely — but pinning to this specific,
  already-verified snapshot for the initial implementation is fine and keeps
  results reproducible. Not committed to git — too large, and it's third-party
  data we don't own; documented as a scripted download step.
- Run (an adapted version of) the original notebook 1 cleaning logic: URL/mention/
  punctuation/stopword/number/emoji removal, lemmatization + stemming, TextBlob
  polarity, 3-bin sentiment labeling, dedupe, null-drop.
- **Fix:** the original hardcoded "take exactly 3915 rows per class" (tuned to
  Taimour's specific snapshot). Replace with dynamic balancing to
  `min(class_counts)` so it's correct for whatever row counts our fresh pull
  produces.
- Commit the resulting small balanced+cleaned dataset
  (`data/cleaned/reviews.csv`, expected a few MB) to git, so cloning the repo
  doesn't require anyone else to repeat the 280MB download / processing wait.
- README must note: accuracy numbers (e.g. Gradient Boosting's reported 90.2%)
  will differ somewhat from Taimour's original figures, since this is a
  different data snapshot/sample — expected, and arguably more legitimate since
  these are numbers this project actually produced.
- Known limitation to document: equal-width `pd.cut` binning of TextBlob polarity
  is a crude labeling heuristic and produces heavy class imbalance pre-balancing;
  the dataset is also multilingual (German/Spanish reviews observed) despite
  English-only preprocessing, which likely limits how meaningful the labels and
  downstream accuracy figures really are. This is framed as an analysis finding,
  not fixed in code (out of scope — YAGNI).

## 4. Notebook fixes (the real technical work)

- **Notebook 3 (LSTM):** original had `Tokenizer(num_words=500)` feeding an
  `Embedding(5000, ...)` layer — vocab mismatch means most tokens end up
  out-of-vocabulary, likely contributing to zero learning (flat loss at
  `ln(3) ≈ 1.0986`, 32.7% test accuracy — at or below random-guess baseline for
  3 balanced classes). Fix the mismatch and right-size the model/epochs to keep
  CPU training under a couple minutes on the ~11-12k row dataset.
- **Notebook 4 (BERT → DistilBERT):** original built a correctly-configured
  `Adam(learning_rate=2e-5, ...)` optimizer object but then called
  `model.compile(optimizer='adam', ...)`, passing the string instead of the
  object — silently falling back to Keras's default LR (0.001), ~50x too high
  for BERT fine-tuning, plausible root cause of the identical flat-loss/32.7%
  failure mode seen in notebook 3. Fix by passing the actual optimizer object.
  Swap `bert-base-uncased` → `distilbert-base-uncased` for CPU-only speed per
  user's compute preference.
- Each notebook gets a short markdown note on what was broken and what fixed
  it — this is itself good portfolio material.
- README "Analysis" section: compare all 9 approaches (7 classical + LSTM +
  DistilBERT) in one results table, with commentary on why classical TF-IDF-based
  models likely outperform deep learning here (small dataset relative to
  TF-IDF's dimensionality, multilingual noise, crude labeling heuristic).

## 5. Dashboard

Fix `dashboard.py` → `dashboard/app.py` and `charts.py` → `dashboard/charts.py`:
correct data/model paths, point the live "submit a review" prediction at the
actual winning model (Gradient Boosting + its vectorizer), handle the missing
logo asset gracefully (skip or use a placeholder), remove the two stub chart
functions (`bubble`, `polar_area`) that currently return hardcoded fake data.
`test.py` (an earlier draft/duplicate of the dashboard) is dropped — not a real
test suite, superseded by `dashboard/app.py`.

Stays a local-run Dash app (per explicit scope decision) — no hosting/deployment
setup.

## 6. Testing & environment

Lightweight `pytest` suite (`tests/test_pipeline.py`): dataset loads with
expected columns, committed models load via `joblib`, and the prediction
function returns one of `{negative, neutral, positive}` for sample input. Not
full TDD — impractical for notebook-driven EDA/training code — but enough to
prove the shipped, runnable pieces actually work.

Single `requirements.txt`, dedicated venv on the existing local Python 3.13 (no
version pinning gymnastics planned up front; if TensorFlow/transformers hit real
install friction on 3.13 during implementation, address it then rather than
guessing now).

## 7. Explicitly out of scope

- Live deployment (Streamlit Cloud / HF Spaces) — local-only per decision.
- Rebuilding the dashboard in a different framework (e.g. Streamlit) — keeping
  Dash per decision.
- Bit-for-bit reproduction of Taimour's exact original accuracy figures — not
  achievable (different data snapshot) and not the goal.
- Committing LSTM/BERT model weights to git.
- Fixing the underlying sentiment-labeling methodology (equal-width polarity
  binning, English-only preprocessing on multilingual text) — documented as a
  known limitation/analysis point, not changed in code.
